# Vegavellum 迭代记录

> 超长程任务模式的逐轮过程记录。每轮必须产出：可执行产物 + 真实 bug/gap + MVP 回归验证。

## 判断标准

一轮迭代是"真实的"当且仅当三条件全满足：
1. **触发是外部压力** — 真实摩擦，非"我感觉缺功能"
2. **产物可执行** — 代码变更 + 通过的验证 + 抓到 bug
3. **完成信号可证伪** — 写不出验证方式的，是想象需求

## 审计方法（感觉"做完了"时强制执行）

| 类型 | 检查内容 |
|------|---------|
| Vertical（跨文件） | 数据 ↔ 页面 ↔ 组件 之间契约一致性 |
| Horizontal（同文件） | 字段定义 ↔ 使用 是否对齐 |
| Connection（传播） | schema 变更是否传播到所有层 |

> **同型字段不一致处理模式**（R27/R28/R29/R31）：sources 与 tags 同为 `string[]` 类型，sources 在 R8 校验了 `Array.isArray`，tags 在 R27 之前未校验。R28 进一步补全 url/license/language 字符串字段的类型校验。R29 扩展到 interface 间：Project interface 字段类型校验完成后（R27/R28），同型的 Category interface 5 字段也应同步校验。R31 扩展到必填 vs 可选：R28 只校验了可选字段（url/license/language），必填字段（name/slug/repo/description/category/addedAt/status）被存在性校验掩盖，未校验 typeof。教训：同型字段应使用同型校验逻辑，TypeScript interface 的每个字段都应在 validator 中执行 typeof/Array.isArray 校验；多个 interface 之间、必填与可选字段之间，同型字段也应同处理。存在性校验（`!== undefined/null/''`）不能替代类型校验（`typeof === 'string'`）。
>
> **validator 健壮性模式**（R31/R32/R36）：`fail()` 设计为"记录错误但继续执行"以报告所有错误，但对类型错误的字段，后续校验假设字符串会导致崩溃（如 `p.repo.split()` TypeError）或误导性错误（如 `Set.has(数组)` 误报"不存在"）。修复方式是在后续校验前加防御性 `typeof` 检查，而非改为"fail 后退出"（那会遗漏其他字段错误）。R31 给 7 处必填字段后续校验加了防御性 typeof，但遗漏了 2 处可选字段独立后续校验（license SPDX、url 冗余），R32 补全。R36 扩展到对象级：YAML 解析结果可能为 null（空文件）或非对象（数组/标量），后续 `p[f]` 访问抛 TypeError。R36 在 projects 循环开头加 null/非对象防御性检查，与 R31/R32 字段级防御、R35 元素级 continue 互补，形成"对象级 + 字段级 + 元素级"三层 validator 健壮性 checklist。教训：validator 健壮性 checklist 应覆盖三层——(1) 对象级（R36：YAML 解析结果 null/非对象防御）、(2) 字段级（R31/R32：必填/可选/跨字段 typeof 防御）、(3) 元素级（R35：数组元素类型错误后 continue 跳过）。新增 validator 校验时，如果校验假设字段/对象是某类型，必须在前面加 typeof 防御，这是 validator 健壮性的 checklist 项。
>
> **格式校验 vs 有效性校验模式**（R34）：正则只校验"形如"，不校验"真实"。R5 用 `/^\d{4}-\d{2}-\d{2}$/` 校验 addedAt 格式，但 `2026-02-30` 形如日期却不是真实日期。R34 用"构造后回读比对"模式补全：`new Date(y, mo-1, d)` 后读取 `getFullYear()/getMonth()/getDate()` 与输入比对，发现溢出即无效。教训：所有日期/数字类格式校验，必须配套有效性校验。正则匹配 ≠ 真实值。validator 契约执行四层闭环：(1) 字段集合（R33）、(2) 字段值类型（R27-R32）、(3) 字段值格式（R5/R9/R11）、(4) 字段值有效性（R34）。
>
> **跨项目唯一性校验模式**（R1/R11/R34）：所有"标识类"字段都应校验跨项目唯一性。R1 覆盖 slug 唯一性，R11 覆盖 category id 唯一性，但 repo 唯一性遗漏到 R34 才补全。R34 选择 `toLowerCase()` 归一化，因为 GitHub owner/repo 解析不区分大小写（`BurntSushi/ripgrep` == `burntSushi/Ripgrep`），不归一化贡献者改大小写即可绕过。教训：标识类字段（slug/category id/repo）唯一性校验需考虑大小写归一化——slug 已被 R11 限制为小写无需归一化，repo 需归一化，未来扩展的标识字段需 case-by-case 判断。
>
> **数组元素级校验模式**（R27/R35）：`string[]` 不只是"字符串数组"，语义上是"非空字符串集合"。R27 给 tags 加了元素 typeof 校验，但遗漏了 sources 同型校验（R35 补全），且两者都遗漏了元素非空和唯一性校验（R35 补全）。R35 确立元素级三层校验：(1) 元素类型（typeof）、(2) 元素非空（`!== ''`）、(3) 元素唯一性（Set 检测）。校验顺序从根本到具体：类型 → 非空 → 唯一 → 枚举（如适用）。`continue` 模式避免同一元素多次报错（类型错误后跳过枚举校验，避免误导性"不在枚举内"）。教训：数组字段（`string[]`）的元素校验同字段级校验一样重要，新增数组字段时必须同步加元素级三层校验。validator 契约执行八层闭环：字段集合（R33）+ 字段值类型/格式/有效性/唯一性（R5/R9/R11/R27-R32/R34）+ 元素值类型/非空/唯一性（R27 tags/R35 sources 同型对齐）。
>
> **空值校验模式**（R36）：可选字段空值（`url: ""` / `license: ""` / `language: ""` / `tags: []` / `sources: []`）与字段省略语义不同。空字符串渲染 `<a href="">` 异常，空数组与省略字段渲染相同但语义矛盾（"显式声明无值"是误写）。R36 确立空值校验：可选字段要么省略不写，要么提供有效值，空字符串/空数组被拒绝。教训：interface 契约不仅是"字段值类型/格式"，也是"字段值语义"——空值与省略是两种不同的意图，validator 必须区分。R35 校验"数组元素非空"（`tags: [cli, ""]` 的 `""` 元素），R36 校验"数组本身非空"（`tags: []`），两者互补覆盖数组字段的两层空性。validator 契约执行九层闭环：对象级防御（R36）+ 字段集合（R33）+ 字段存在性（R1）+ 字段值类型/格式/有效性/唯一性（R5/R9/R11/R27-R32/R34）+ 字段值空性（R36）+ 元素值类型/非空/唯一性（R27 tags/R35 sources）。
>
> **空白字符串校验模式**（R37）：R36 校验"空字符串"（`=== ''`），但遗漏"空白字符串"（`trim() === ''`）。`name: "   "` 通过必填校验（非空字符串 truthy）和 typeof 校验（是字符串），但渲染为不可见空白——标题/描述/图标消失，用户无法识别。R37 将空值校验从"字面空"扩展到"语义空"：`name.trim() === ''` 拒绝仅含空格/制表符/换行的字符串。R37 覆盖 Project name/description（必填 free-text）+ license/language（可选字符串）+ Category id/name/name_en/icon/description（全部 5 个 free-text 字段），同型对齐 Project 和 Category interface。教训：空值校验模式必须配套 trim() 检查，"字面空"（`=== ''`）和"语义空"（`trim() === ''`）是两层不同的空性，两者都需校验。
>
> **横向审计：同型访问路径全覆盖模式**（R38）：R37 修复了 `for (const c of categories)` 循环内的 null 崩溃，但漏掉循环**之前**的 `categories.map((c) => c.id)`（第 66 行计算 categoryIds），`- null` 仍在此处崩溃。R37 攻击样本验证才暴露此 gap，触发 R38 紧急修复。教训：**修复一处防御性检查时，必须审计所有"遍历该数组 + 访问字段"的代码路径**，包括：(1) 循环内访问（for / forEach / for...of）、(2) 循环前预处理（.map / .filter / .reduce）、(3) 循环后聚合（.find / .some / .every）。任何一处遗漏都会使防御性检查失效。R38 同时确立"职责分离"模式：filter 只做 null-safe 过滤不报错，报错由专门的 for 循环检查负责——避免错误信息和实际数据状态不一致。validator 健壮性 checklist 扩展：对象级防御需覆盖所有同型访问路径，validator 契约执行十层闭环：对象级（R36 + R38 同型路径全覆盖）+ 字段集合（R33）+ 字段存在性（R1）+ 字段值类型/格式/有效性/唯一性（R5/R9/R11/R27-R32/R34）+ 字段值空性（R36）+ 字段值 trim 空性（R37）+ 元素值类型/非空/唯一性（R27 tags/R35 sources）。
>
> **攻击样本验证模式**（R37/R38/R39）：R37 修复后通过 `npm run validate` 和 `npm run build` 真实数据回归（0 错误 0 警告），但**没有**通过攻击样本验证。R37 攻击样本验证（临时脚本 `_r37-smoke.mjs` 构造 5 类非法 YAML）才暴露 R37 修复不完整 → 触发 R38。R38 后的横向审计再次通过攻击样本验证（`_r39-pre-audit.mjs`）确认 R39 gap（tags/sources 元素空白字符串）。教训：真实数据回归只能证明"已有数据不破坏"，**不能**证明"非法数据被正确拒绝"。任何防御性修复都必须配套攻击样本验证：构造非法 YAML → 运行 validator → 验证错误信息符合预期。否则修复可能不完整，validator 可能在到达防御性检查之前就崩溃。攻击样本验证是 validator 健壮性的最终防线，与真实数据回归互补。
>
> **同型对齐全覆盖模式**（R36/R37/R38/R39）：trim() 空白校验从字段级（R37）扩展到元素级（R39），与对象级（R36/R37）+ 字段级（R37）+ 元素级（R39）三层闭环。R36→R37 是对象级同型对齐（Project → Category），R37→R39 是层级同型对齐（字段级 → 元素级）。R38 是横向同型对齐（循环内 → 循环前预处理）。教训：**同型对齐必须覆盖所有层级和所有路径**——(1) 对象级（YAML 解析结果 null/非对象防御，R36 Project + R37 Category + R38 循环前预处理）、(2) 字段级（free-text 字段 trim() 空白校验，R37 Project name/description/license/language + Category 5 字段）、(3) 元素级（数组元素 trim() 空白校验，R39 tags + sources）。任何一层遗漏都会使 validator 契约执行出现盲区。R31 模式在 R39 再次确认：空性校验（trim() 空白）必须在枚举校验之前 `continue`，避免误导性"不在枚举内"错误掩盖真实问题。validator 契约执行十一层闭环：对象级（R36 + R37 + R38）+ 字段集合（R33）+ 字段存在性（R1）+ 字段值类型/格式/有效性/唯一性（R5/R9/R11/R27-R32/R34）+ 字段值空性（R36）+ 字段值 trim 空性（R37）+ 元素值类型/非空/唯一性（R27 tags/R35 sources）+ 元素值 trim 空性（R39）。
